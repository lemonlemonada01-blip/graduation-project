# 🧠 Engine Architecture, Complexity & Data Storage Breakdown

This document provides a comprehensive technical overview of how your Plagiarism Engine operates under the hood, how it achieves high performance, and exactly where your data is stored locally.

---

## 1. ⚙️ The Underlying Mechanism

The engine operates in two distinct phases: **Indexing (Crawling)** and **Scanning (Matching)**.

### Phase A: Indexing Pipeline
1. **Surgical Crawling (`extractor.py`)**: The crawler walks through your project directory but skips 95%+ of boilerplate and autogenerated files (like `.dart_tool`, `node_modules`, `Pods`, `build`, etc.).
2. **Domain Classification**: Based on the file extension, the file is classified as either **Source Code** (`.py`, `.dart`, `.cpp`, etc.) or a **Multilingual Document** (`.pdf`, `.md`, `.docx`, etc.).
3. **Lazy Model Dispatch (`vector_store.py`)**: 
   - If it's a code file, the engine lazily loads `codebert-base`.
   - If it's a document, the engine lazily loads the `MultilingualDocumentEnsemble` (e.g., `bge-m3` or `LaBSE`).
4. **Vector Embedding**: The models convert the semantic meaning of the file into a dense, high-dimensional vector array.
5. **Structural Fingerprinting (`code_detector.py`)**: For code, the engine also tokenizes the syntax (using Python AST or Pygments) into a structural fingerprint to detect variable renaming or logic shuffling.

### Phase B: Cross-Scanning Pipeline
1. **Database Retrieval (`db.py`)**: The engine pulls the catalog of indexed projects from PostgreSQL instantly.
2. **Pairwise Comparison**: Every project is compared against every other project in the database.
3. **Similarity Scoring**: 
   - **Semantic Score**: Uses Cosine Similarity between vector embeddings.
   - **Structural Score**: Uses Sequence Matching on the code token fingerprints.
4. **Report Generation**: Outputs a combined similarity percentage and flags highly suspicious pairs.

## 2. 🗄️ Where Exactly is the Data Stored?

Your data is distributed across three isolated storage systems, all kept strictly **100% offline and local** on your machine.

> [!IMPORTANT]
> **Data Privacy Guarantee:** No code, document, or embedding ever leaves your PC. Everything is processed offline.

### A. The Models (Weights & Brains)
- **Location**: `D:\AI engine\models\`
- **Contents**: The 8 HuggingFace models (`codebert-base`, `bge-m3`, `arabertv02`, etc.) in `.bin` or `.safetensors` format.

### B. The Vector Databases (Semantic Embeddings)
- **Location**: `D:\AI engine\chroma_code_db\` and `D:\AI engine\chroma_multilingual_docs_db\`
- **Contents**: Local ChromaDB instances powered by SQLite and HNSW (Hierarchical Navigable Small World) indices. 
- **Purpose**: Stores the mathematical vector representations of your files. Code vectors are strictly isolated from NLP document vectors to prevent cross-contamination.

### C. The Relational Database (Metadata & Reports)
- **Location**: `postgresql://postgres:postgres@localhost:5432/plagiarism_engine_db` (Running locally on PostgreSQL service `postgresql-x64-18`).
- **Contents**: 
  - **`projects` table**: Metadata about the indexed projects.
  - **`project_files` table**: File paths, extensions, and structural fingerprints.
  - **`scan_reports` & `suspicious_pairs` tables**: The final generated plagiarism reports and flagged matches.

## 3. ⏱️ Time Complexity (Algorithm Speed)

The engine has been hyper-optimized to handle giant monorepos without stalling.

- **File Crawling**: $O(N)$ where $N$ is the number of files. Highly optimized by skipping giant build directories.
- **Vector Search (ChromaDB)**: $O(V \cdot \log(V))$ where $V$ is the number of vectors. Using the HNSW algorithm, searching through millions of embeddings takes milliseconds.
- **Structural Code Matching (`SequenceMatcher`)**: 
  - Traditionally, this algorithm is $O(T^2)$ where $T$ is the number of tokens. For a 10,000-line file, $10,000^2$ operations would freeze the CPU.
  - **The Fix**: We cap $T$ at a maximum of `1,500` tokens (`fp1[:1500]`). This changes the complexity to **$O(1)$ constant time limit**. It ensures the sequence matcher always completes in fractions of a second, regardless of how massive the monorepo file is.

## 4. 🧠 Memory Efficiency & Performance

Running 8 AI models simultaneously would normally crash a consumer PC by exceeding available RAM/VRAM. The engine solves this via:

> [!TIP]
> **LazyModelPool Singleton**
> Instead of loading all 8 models at boot, `vector_store.py` uses an on-demand singleton pattern. 
> - It only loads `codebert-base` into RAM when a code file is encountered.
> - If an Arabic PDF is found, it loads `arabertv02`.
> - This keeps your idle RAM usage near zero, and peak RAM usage strictly bounded to the active task.

- **NUL Byte Sanitization**: PostgreSQL crashes if a file contains a hidden C-style null byte (`\x00`). Our `clean_str()` function sanitizes all data before it hits the DB, preventing fatal driver crashes.
- **Batch Processing**: Instead of processing embeddings one by one, the engine batches them, taking advantage of vectorized PyTorch operations for maximum CPU/GPU throughput.
